## Next decisions (user picks one at a time)

The user's instruction was to record this and then follow up
**one at a time**. The candidate next steps, in priority order:

### A — Tailscale auth + Tauri 2 scaffold (daily-driver path)
- Pros: gets Gundam Halo to a state where the user can actually
  use it as their second system (Mac + phone reach)
- Cons: Tauri 2 scaffolding is mechanical but voluminous
  (menubar tray, single binary, permissions)
- Estimated scope: 1 sprint (≈ 6–10 commits)

### B — M14 project dispatch (core value path)
- Pros: **this is the whole reason Gundam Halo exists** —
  per-project isolation so Hermes's "single growing context"
  problem goes away. Highest leverage work.
- Cons: design decisions needed (file layout, dispatch model,
  context inheritance rules). Should be a plan, not a hot fix.
- Estimated scope: 1–2 sprints

### C — Live smoke run (demo path)
- Pros: zero risk, confirms what's already in the codebase
  actually works against real MiniMax API + real Mac + real
  Hermès coexistence
- Cons: not durable — a smoke run is a snapshot, not progress
- Estimated scope: 1 hour

### D — Fork 3-track cleanup plan (baselining path)
- Pros: kills the 55 pre-existing fails, makes every future
  PR cleaner, concentrates the 40 router-mount fixes into one
  `app/main.py` edit
- Cons: infra work, not user-visible. Has to be done eventually
  but not the most exciting ticket.
- Estimated scope: 1 plan (3 parallel tracks, 1 integration gate)

**My recommendation**: B first, then D, then A. M14 is the
core value and unblocks every other workflow; cleaning the
baseline second means future M14+ work doesn't trip over
pre-existing test noise; A is the last-mile packaging once
the core experience is worth packaging.
