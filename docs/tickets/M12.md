## Context

Today's memory layer is two file trees:

1. `~/.gundam-halo/projects/<name>/conversations/<sid>.json` — one
   JSON per session, holds full message history.
2. `~/.gundam-halo/memory/users/<user>/<slug>.md` + `_index.json` —
   per-user key/value notes the agent writes.

Both are human-readable (great) and atomic (great) but **not
queryable** beyond:

- "load this exact session by id"
- "list this user's key/value notes"

You cannot ask: "what did Ken say about the Unicorn model 3 weeks
ago across all projects and all channels?" or "show me every tool
call in the last 24h". To answer those you scan every JSON.

The README also implies "Mavis remembers" (per the Gundam Halo
product story), but with the current store, every conversation is
a fresh context window — there's no semantic continuity.

## Goal

Add a **SQLite index** + **FAISS vector index** that layer on top
of the existing file store. Files remain the source of truth
(human-readable, easy to back up, easy to grep). SQLite is a
queryable index. FAISS is a semantic recall index.

| Layer | Purpose | Source of truth? |
|---|---|---|
| JSON / MD files | Full content, human-readable | ✅ yes |
| SQLite | Index for fast queries (list, count, filter) | ❌ derived |
| FAISS | Vector recall ("find similar past context") | ❌ derived |

Both derived layers must be **rebuildable from disk**. If SQLite
or FAISS goes corrupt, the user can nuke the index and we rebuild
it from the JSON/MD files in seconds (for a few thousand messages).

## Design

### Storage layout (under HALO_HOME)

```
memory/
    index.sqlite                # NEW: SQLite database
    vectors.faiss               # NEW: FAISS index (IndexFlatIP, cosine via L2 norm)
    vectors.meta.json           # NEW: vector_id -> (kind, source_id, chunk)
    users/                      # existing
projects/
    <name>/
        conversations/
            <sid>.json          # existing — remains source of truth
```

The `vectors.faiss` lives next to SQLite because they're paired
(you can never have one without rebuilding the other).

### SQLite schema

```sql
-- One row per session.
CREATE TABLE sessions (
    session_id    TEXT PRIMARY KEY,    -- uuid hex
    project_name  TEXT NOT NULL,
    agent_type    TEXT NOT NULL,
    created_at    REAL NOT NULL,       -- unix ts
    updated_at    REAL NOT NULL,
    message_count INTEGER NOT NULL DEFAULT 0,
    channel       TEXT                 -- 'web' | 'telegram' | ...
);

CREATE INDEX idx_sessions_project ON sessions(project_name);
CREATE INDEX idx_sessions_updated ON sessions(updated_at DESC);

-- One row per message in a session.
CREATE TABLE messages (
    message_id    INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    seq           INTEGER NOT NULL,    -- order within session (0, 1, 2 ...)
    role          TEXT NOT NULL,       -- 'system' | 'user' | 'assistant' | 'tool'
    content       TEXT NOT NULL,
    tool_calls    TEXT,                -- JSON array, NULL if none
    tool_call_id  TEXT,
    name          TEXT,
    created_at    REAL NOT NULL,
    UNIQUE (session_id, seq)
);

CREATE INDEX idx_messages_session ON messages(session_id, seq);

-- Threads: a "thread" groups sessions by topic.
-- For v0.2.0 we keep this simple — auto-derived from project
-- (one project = one thread). The schema supports user-assigned
-- threads later.
CREATE TABLE threads (
    thread_id     TEXT PRIMARY KEY,
    name          TEXT NOT NULL,
    project_name  TEXT,
    created_at    REAL NOT NULL,
    updated_at    REAL NOT NULL
);

CREATE TABLE session_thread (
    session_id    TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    thread_id     TEXT NOT NULL REFERENCES threads(thread_id) ON DELETE CASCADE,
    PRIMARY KEY (session_id, thread_id)
);
```

### FAISS index

- `IndexFlatIP` with L2-normalized vectors (= cosine similarity).
- Default dimension: 384 (matches `all-MiniLM-L6-v2` via
  `sentence-transformers` if available, else a 384-dim hash
  embedding — see Embedding section).
- Stored as `memory/vectors.faiss`.
- Metadata sidecar `memory/vectors.meta.json` maps
  `vector_id (int) -> {kind: "message"|"memory_entry", source_id: str, chunk: str}`.

### Embedding strategy

Two paths, pick at runtime via config:

1. **Real model (preferred)** — `sentence-transformers/all-MiniLM-L6-v2`,
   384-dim, runs on MPS on Mac. Lazy-imported; if the lib or
   model isn't installed, we fall back to path 2.
2. **Hash embedding (fallback)** — `numpy` only. SHA-256 of
   normalized tokens → 384-dim sparse vector → L2-normalized.
   Quality is poor (no semantic meaning) but it's *deterministic
   and offline*, so tests work without a model download.

The choice is in `Config.memory.embedding_backend: "model" | "hash"`
(default `"hash"` for v0.2.0; we'll flip to `"model"` once we
ship the model download in a follow-up).

### Index lifecycle

- **On session save** (`persistence.save_messages`): after the
  JSON is written, we upsert the session + all messages into
  SQLite, then enqueue new chunks for embedding.
- **Embedding is async** — we use a `BackgroundEmbedder` (in-process
  queue + worker thread) so the HTTP response doesn't wait for
  the model. Best-effort; if embedding fails, the SQLite index
  still has the message, just not its vector.
- **On startup**: we check SQLite exists, FAISS exists; if either
  is missing we run `rebuild_index()` which scans every JSON +
  every user-memory file and re-inserts.
- **`POST /api/memory/rebuild`** — admin endpoint, idempotent,
  runs `rebuild_index()`. Useful after data import.

### Public API (additive, no breaking changes)

```
GET  /api/memory/sessions                  list all sessions (paginated, ?project=&limit=&offset=)
GET  /api/memory/sessions/{sid}/messages   already exists as /api/sessions/{sid}/messages — kept
GET  /api/memory/sessions/{sid}            session metadata
GET  /api/memory/recall?q=...&k=5          semantic recall across messages + memory entries
GET  /api/memory/search?q=...&project=...  LIKE search across messages
POST /api/memory/rebuild                   admin: rebuild SQLite + FAISS from disk
```

`/api/memory/recall` returns:

```json
{
    "query": "what did Ken say about the Unicorn model",
    "k": 5,
    "results": [
        {
            "kind": "message",
            "session_id": "abc123",
            "project": "gundam-design",
            "seq": 4,
            "role": "user",
            "snippet": "...the Unicorn's psychoframe awakened...",
            "score": 0.82
        },
        {
            "kind": "memory_entry",
            "user": "ken",
            "key": "favorite_gundam",
            "value": "Unicorn",
            "score": 0.65
        }
    ]
}
```

### Threading model

- `BackgroundEmbedder` uses one worker thread + an unbounded
  `queue.Queue` for now. v0.3+ can swap to a real thread pool.
- SQLite access from the worker: we open a **separate connection**
  per thread (`check_same_thread=False`). WAL mode is enabled
  in `init()` so reads don't block writes.
- FAISS: the index is rebuilt by `faiss.write_index()` after
  mutation. We hold an in-memory copy (`index.ntotal` grows
  in-process) and persist on every batch boundary. On startup
  we read FAISS back from disk.

### Scope cuts (deferred to M12.5 / M13)

- **Cross-project threads** (today thread = project). Will add
  manual `thread_id` assignment in a follow-up.
- **Embedding model download + warmup** (we ship the *path*,
  hash fallback for v0.2.0).
- **Telegram channel integration** (sessions from Telegram need
  to be persisted via the same path; not part of this ticket).
- **Memory decay / TTL** (we keep everything forever for v0.2.0).
- **Multi-user FAISS** (one index for everyone; per-user isolation
  happens at the SQL filter level — results are filtered by
  `user` in recall if `?user=ken` is passed).

## Known follow-ups (out of scope)

1. Real `sentence-transformers` model warmup + download script.
2. Per-thread summarization (use LLM to compress a thread into a
   1-paragraph recap, store as `threads.summary`).
3. Recall feedback loop: when a recall result is "used" in an
   agent reply, bump its score so the next time the same query
   appears, the same chunk surfaces.
4. Export memory as a single JSON dump (for backup / migration).
5. **Apple Silicon faiss-cpu + torch MPS finalization crash** —
   in mixed-mode test runs, having `faiss-cpu` already loaded
   when `torch` later imports can crash the Python process. We
   mitigate in tests by:
   - defaulting `Config.memory.disable_vector_index = True` in
     `tests/memory/conftest.py` + `tests/api/conftest.py`
   - marking the dedicated FAISS tests with `@pytest.mark.faiss_native`
   - skipping those by default via `addopts = "-m 'not faiss_native'"`
   The real fix lands in M12.1 (separate faiss/torch init order
   in the live app) or upstream (faiss-cpu vs torch MPS).

## Why this matters

Right now, every conversation with Gundam Halo is a cold start.
After M12:

- "Mavis, 之前我哋傾過咩關於 NT-D？" → real answer, not "I don't
  remember."
- Dashboard can show "last 10 sessions across all projects" with
  filters — currently impossible without scanning every JSON.
- Audit dashboard (B7) can do "show me every tool call from the
  last 7 days" in O(1) instead of O(n) JSON parses.
- Cantonese fine-tune data (M9-E) can be sourced from
  `recall(q="粵語", k=1000)` instead of hand-curating.

The whole product promise of "your AI remembers" finally
materializes. Currently it doesn't — and the README is wrong.
