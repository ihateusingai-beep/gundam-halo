## Context

The security audit log lived as a 117-line `SecurityTab` buried
inside the Settings page. It worked but was a strip: 96px-tall
scroll region inside a 1-of-7 settings tab. Hard to use as a daily
review surface, no expand-to-inspect, no filter on `target` field,
no date bucketing. Plan B's "mission control" theme calls for a
proper first-class view.

B7 lifts the audit log out of Settings into a dedicated route at
`/audit`, with proper cockpit framing, stat cards, search, expand,
and a deep-link from the command palette.

| Feature | How |
|---|---|

| **4 stat cards** | TOTAL / TODAY / BLOCKED / UNIQUE ACTIONS — computed from the unfiltered list so the header always reflects the actual log regardless of current filter |

| **Empty states** | (a) log is empty → reticle + "NO AUDIT TRAIL" + helper text; (b) filter matches nothing → "// no entries match current filters" |
| **Cockpit framing** | All entries use `HudCard`, `Reticle`, `StatusDot`, `gundam-timeline`, `gundam-memory-card` — same visual language as B2, settings, project memory |

### Scope clarification (important)

The audit log **only subscribes to MAC_OP_* event types** in the
backend (`audit.py:103`) — i.e. Mac control operations (file I/O,
shell, policy blocks). The dashboard title and subtitle are
deliberately scoped to match. Other event categories
(LLM inference, tool calls, voice turns, etc.) flow through the
ActivityTicker instead — that's the right surface for live
transient events, while the audit log is the right surface for
**persisted, security-relevant, post-hoc review** of Mac ops.

If the user later wants a full event-bus viewer, that's a
different deliverable (would need backend to subscribe the audit
logger to all EventTypes, or build a separate "telemetry replay"
page). B7 is specifically the **security audit** view.

### Code structure

- **`AuditDashboardPage`** — main component. Local state for
  entries, loading, error, filter type, target query, expand map.
  `useEffect` for initial load; `refresh()` callable for the button.
- **`useMemo` derivations** — `stats`, `filtered`, `groups`,
  `eventTypes` all derive from the same source. Stats are computed
  from the unfiltered list; the rest from `filtered`.
- **`groupByDate()`** — extracted helper. Same algorithm as
  `memory.tsx` (B2 reuse — copy-paste-with-acknowledgment, since
  coupling a tiny helper across 2 routes would be over-engineering
  for ~15 lines).
- **`AuditNode`** — per-entry card. Two render layers: collapsed
  (time / type / action / target / right-side metadata) and
  expanded (full `DataTable` + `id` + `ts`).
- **`DataTable`** — 2-column `<table>` renderer for `data.*` keys,
  with `JSON.stringify` for nested objects. Renders `(no data)`
  for empty objects.
- **`Header`** — separate component so the stat cards live with
  the title (1 HudCard).
- **`StatCard`** — small presentational helper.
- **`formatTime` / `formatBytes` / `formatMs`** — local helpers,
  each <10 lines. Pure, no React.

### Data flow

```
backend audit.log  ──▶  api.getAuditLog(500)
                          │
                          ▼
                       entries[]  (raw NDJSON → JSON array)
                          │
                          ▼
                       useMemo derivations:
                         stats (unfiltered)
                         filtered (after type+target filters)
                         groups (date buckets)
                          │
                          ▼
                       render: Header + FilterBar + Timeline
```

No mutations, no global state, no zustand. Pure render-level
filtering on top of the API response.
