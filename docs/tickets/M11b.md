## Context

The 2026-06-12 audit flagged:

> "**8 themes on the dashboard, 1 responder on the backend.** Theme
> switcher affects CSS only; Live2D-trigger behavior is
> theme-agnostic."

Switching from NT-D to GOD in the cockpit today: the colors
change, the cockpit border changes, the button text changes —
but when the agent responds, the Live2D `expression: ntd_calm`
emission comes back regardless. The avatar's reaction to a
psychoframe awakening looks identical whether the user picked
the Unicorn or the Burning mode.

This commit ships a per-theme responder for all 8 themes so
the Live2D trigger vocabulary matches the chosen cockpit.

## What landed (2026-06-12, this session)

### New base class

**File**: `backend/app/voice/live2d/base_responder.py` (215 lines)

`BaseThemeResponder(Live2DInterface)` — shared implementation that
every concrete theme responder inherits. Owns:

- `__init__` — config + model_path + metadata loading
- `_find_model3` — recursive `.model3.json` lookup
- `warmup` — validates fallback expressions + motion groups
- `trigger` — validate-or-emit-best-effort + log
- `expressions` / `motion_groups` / `model_name` properties

Subclasses declare exactly three class attributes:

1. `THEME_ID: str` — the short slug (e.g. `"seed"`)
2. `FALLBACK_EXPRESSIONS: list[str]` — placeholder expression names
3. `FALLBACK_MOTION_GROUPS: list[str]` — placeholder motion groups

The base class **refuses to instantiate a subclass that omits any
of the three** (validation in `__init__`). This forces a
consistent interface across the 8 theme responders.

### NTDResponder refactored to use the base

**File**: `backend/app/voice/live2d/ntd_responder.py` (-178 lines net)

The 195-line `NTDResponder` is now a 32-line thin subclass that
just declares `THEME_ID` + the two fallback lists. All the
shared logic (`_find_model3`, validation, properties) is
inherited from `BaseThemeResponder`. **No behavior change** —
all existing NTDResponder tests still pass.

### Factory rewritten

**File**: `backend/app/voice/live2d/live2d_factory.py`

```python
_THEME_RESPONDERS = {
    "ntd": NTDResponder,
    "seed": SeedFreedomResponder,
    "crossbone": CrossboneResponder,
    "gundam-ntd-green": GreenNTDResponder,
    "gundam-00": DoubleOResponder,
    "gundam-destiny": DestinyResponder,
    "gundam-god": GodResponder,
    "gundam-cartoon": CartoonResponder,
}

# Frontend long-form → backend short-form
LONG_TO_SHORT = {
    "gundam-ntd": "ntd",
    "gundam-seed": "seed",
    "gundam-crossbone": "crossbone",
    # the other 5 are already short
}
```

Plus a new `available_themes()` helper that returns the sorted
list of registered short keys — useful for diagnostic UIs and
the upcoming `POST /api/live2d/theme` endpoint (follow-up sprint).

### Behavior

`create_live2d(config)` now:

1. Reads `config.voice.live2d.theme` (or accepts an explicit
   config)
2. Resolves frontend long-form → backend short-form via
   `LONG_TO_SHORT`
3. Looks up the responder class in `_THEME_RESPONDERS`
4. Raises `ValueError` with the full list of available themes
   if the lookup fails

### What's NOT done (deliberately)

- **Frontend theme switch → backend responder swap is one-way**:
  the dashboard's `setTheme` only updates `data-theme` (CSS layer)
  and localStorage. It does NOT POST to the backend to swap the
  responder. Two paths to close this gap (deferred — separate
  ticket):
  1. `POST /api/live2d/theme` endpoint that calls
     `create_live2d(new_config)` and rebinds `HaloResponder._live2d`
  2. Frontend `useThemeStore.setTheme` calls the new endpoint
     after the local state update
- **Per-theme `EMOTION_MAP`** in `halo_responder.py` is still
  NT-D-only. The current code passes raw expression / motion
  names to `trigger()`, so the same emotion string ("awakening")
  triggers the *NT-D* expression `ntd_psychoframe` regardless of
  theme. The 7 new responders will fire on tool calls (via
  `tool_motion_mapper`) but not yet on the LLM-emitted
  emotion DSL. Closing this gap is a small follow-up — extend
  `EMOTION_MAP` to a `dict[str, EMOTION_MAP]` keyed by
  `THEME_ID`.
- **CSS layer unchanged** — frontend `gundam.css` already has 8
  `[data-theme="gundam-X"]` selectors; M11b does not touch CSS.

## Follow-ups (next sprint candidates)

1. **`POST /api/live2d/theme` endpoint** — let the dashboard
   actually swap the responder at runtime, not just at startup.
2. **Per-theme `EMOTION_MAP`** — extend
   `halo_responder.EMOTION_MAP` from a flat dict to a
   `dict[str, EMOTION_MAP]` keyed by `THEME_ID`. The LLM-emitted
   emotion DSL would then resolve to the right theme's
   expression / motion pair.
3. **Real model files for the 7 new themes** — currently the
   fallback lists emit raw names. The frontend can still try to
   play them, but a real `.model3.json` per theme would let
   the responder's `warmup` validate against the actual
   asset catalog. (User has the model metadata system from
   M3 already; this is just "drop in 7 more .model3.json".)
4. **Per-theme `TOOL_MOTION_MAP`** — currently
   `tool_motion_mapper.TOOL_MOTION_MAP` is NT-D-only. The 7
   new responders will get tool-call triggers using their
   own expression/motion names once `map_start` / `map_end`
   accept a theme arg.
